## Key Contracts

```js
// routes/budgets.js
router.get('/', ...)     // -> 200 [budget, ...] (status='active' only, unless ?status=archived)
router.post('/', requirePermission('inference:manage'), ...)
  // body: { scope_type, scope_value, period, limit_usd, mode }
  // validates scope_type/period/mode against the same allowlists as the DB
  // CHECK constraints (S1.1) BEFORE hitting the DB — 400 on invalid, not a
  // raw Postgres constraint-violation error surfacing to the client
  // -> 201 { id, scope_type, scope_value, period, limit_usd, mode, status: 'active', ... }
router.put('/:id', requirePermission('inference:manage'), ...)
  // body: any subset of { scope_value, period, limit_usd, mode } — scope_type is immutable after creation (changing it would silently repoint an existing budget's enforcement target)
  // -> 200 updated row
router.delete('/:id', requirePermission('inference:manage'), ...)
  // Soft-archive: UPDATE usage_budgets SET status='archived' WHERE id=$1.
  // Not a hard DELETE — checkBudget()'s WHERE status='active' filter (S1.1)
  // means an archived budget is simply never matched again; no changes
  // needed to enforcement/escalation code. Also preserves history, which
  // matters on a governance platform (vision.md's "Auditability" outcome).
  // -> 200 archived row (not 204 — frontend needs it to update the table)
```

## Key Decisions

- **D1 — DELETE archives, doesn't hard-delete.** `usage_budgets.status`
  already has an `'archived'` value (defined in S1.1's migration for
  exactly this). No FK points *to* `usage_budgets`, so a hard delete would
  be technically safe — but archiving preserves the audit trail and
  requires zero changes to `checkBudget()`'s existing `status = 'active'`
  filter.
- **D2 — `scope_type` is immutable after creation.** `PUT /:id` accepts
  `scope_value`/`period`/`limit_usd`/`mode` but not `scope_type` — changing
  which *kind* of scope a budget targets after the fact would silently
  repoint enforcement onto a different dimension, which is a create-a-new-
  budget action, not an edit.
- **D3 — server-side validation mirrors the DB CHECK constraints, not just
  DB error passthrough.** A raw Postgres constraint violation is a bad API
  error (500, cryptic). Validate `scope_type`/`period`/`mode` against the
  same allowlists as the DB constraints *before* the query, matching
  `models.js`'s `status` PATCH validation pattern (`VALID.includes(status)`
  → 400).
- **Follows `TagAdmin.jsx`, not `WaiverAdmin.jsx`.** `design.md`'s original
  epic-level comparison ("same shape as WaiverAdmin.jsx") was wrong —
  `WaiverAdmin.jsx` is decide-only (approve/deny an existing request), no
  create/edit form at all. `TagAdmin.jsx` is the actual CRUD precedent.

## Acceptance Criteria

**MUST:**
1. All 4 scenarios in `s1.4-story.md` pass
2. `scope_type`/`period`/`mode` validated server-side against the same
   allowlists as the DB CHECK constraints, returning 400 (not a raw DB
   error) on violation
3. `DELETE /:id` archives (status update), never a hard row delete
4. `PUT /:id` cannot change `scope_type`
5. Page reachable at `/admin/budgets`, listed in the Administration nav

**MUST NOT:**
1. Must not allow editing `scope_type` through the UI or API
2. Must not hard-delete a budget row through any code path
