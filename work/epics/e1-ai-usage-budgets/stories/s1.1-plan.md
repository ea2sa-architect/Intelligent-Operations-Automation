## Execution Order

```
Task 1 (migration) ──┐
                       ├──► Task 3 (checkBudget) ──► Task 4 (manual verification)
Task 2 (helpers) ─────┘
```

Tasks 1 and 2 have no mutual dependency — schema and pure-function helpers
don't touch each other. Sequenced schema-first (Task 1 before Task 2) so
Task 2's helpers and Task 3's queries are written against concrete column
names/types rather than guessed ones, even though nothing strictly blocks
doing Task 2 first.

Risk-first note: Task 2's calendar-window logic (D1) is the most likely
place for a subtle bug (UTC boundary handling) — Task 4 exists specifically
to catch what Task 2's mocked unit tests structurally cannot: whether
`computePeriodStart()`'s output actually lines up with what Postgres's
`TIMESTAMPTZ` comparison does with it.

## Risks

| Risk | L/I | Mitigation |
|------|:---:|------------|
| Mocked unit tests (Task 3) pass while the real SQL/timezone behavior is wrong | M/M | Task 4's manual verification against real Postgres is not optional — it's the only place this codebase can catch it, since no automated integration-test infra exists yet (CLAUDE.md — "What has NOT been built yet") |
| `limit_usd NUMERIC(10,6)` returned from `pg` as a string (node-postgres does this for NUMERIC by default), breaking `>=` threshold comparisons if not parsed | M/M | Task 3's tests explicitly assert `spent_usd`/`limit_usd` are JS numbers in the returned shape, not raw driver strings — catches this before Task 4 |
| Task 2's helpers get over-built (e.g. supporting periods beyond daily/monthly) | L/L | Design.md and story.md only specify `daily`/`monthly` — Task 2 implements exactly those two, nothing speculative |
