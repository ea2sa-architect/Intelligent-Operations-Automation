# S1.1 Design: Budget schema + spend-check

## What & Why

**Problem:** `ai-inference-service` already tracks cost per request
(`estimated_cost_usd`, EP-102), but there's no concept of a spend *limit*
for any scope — no way to ask "has team-x gone over budget this month."

**Value:** Every later story in this epic (S1.2 enforcement, S1.3
escalation, S1.4 admin UI) needs the same answer to that question. Building
it once here, tested, means none of them reimplement spend aggregation
independently or drift from each other's definition of "over budget."

## Approach

Add `usage_budgets` (one row per scope+period+limit+mode) and a pure
`checkBudget({ scopeType, scopeValue })` function that: looks up an active
budget for that scope, sums `estimated_cost_usd` from `inference_requests`
within the current calendar period, and returns `ok`/`warn`/`breach`
against the limit.

**Components:**

| Component | Change | File |
|---|---|---|
| `usage_budgets` table | create | `db/migrations/ai_inference/004_usage_budgets.sql` |
| `checkBudget()` | create | `services/ai-inference-service/src/lib/spend-check.js` |
| Unit tests | create | `services/ai-inference-service/tests/spend-check.test.js` |

**Missing-entity strategy (PAT-E-523):** no budget row for a scope is not
an error — `checkBudget()` returns `{status: 'ok', budget: null}`. Budgets
are opt-in; treating the common case (no budget defined) as a failure would
be wrong.

**Value preservation (PAT-E-572):** this isn't a pass-through wrapper
around a SQL query. It encodes three pieces of real domain logic: (1)
calendar-period window computation, (2) the warn/breach threshold policy
(80%/100%), (3) safe scope-type → column dispatch. Each of those would
otherwise be reimplemented, and likely inconsistently, in S1.2/S1.3/S1.4.

## Key Decisions

- **D1 — Calendar windows, not rolling.** `monthly` = since the 1st of the
  current month UTC; `daily` = since 00:00 UTC today. Matches the
  "budget resets" mental model, and this codebase's existing convention
  (audit-service's monthly range partitioning) rather than inventing a
  rolling-window concept.
- **D2 — scope_type → column via a fixed allowlist, not string
  interpolation.** `scope_type` will eventually be admin-supplied (S1.4's
  CRUD). It gets dispatched through a literal `{model_id: 'model_id', user_id: 'user_id', service_id: 'service_id', workflow_id: 'workflow_id'}`
  map — reject anything not in that map — never interpolated directly into
  the SQL column reference.
- **D3 — No budget = `ok`, not an error.** See missing-entity strategy
  above.

## Examples

**Setup — a budget exists:**
```sql
INSERT INTO ai_inference.usage_budgets
  (scope_type, scope_value, period, limit_usd, mode, status)
VALUES ('user_id', 'team-x', 'monthly', 100.00, 'soft', 'active');
```

**Usage — spend under limit:**
```js
import spendCheck from '../src/lib/spend-check.js';

const result = await spendCheck.checkBudget({ scopeType: 'user_id', scopeValue: 'team-x' });
// => {
//   status: 'ok',
//   budget: { id: '...', scope_type: 'user_id', scope_value: 'team-x',
//             period: 'monthly', limit_usd: '100.00', mode: 'soft', status: 'active' },
//   spent_usd: 40,
//   limit_usd: 100,
// }
```

**Usage — no budget bound to this scope:**
```js
const result = await spendCheck.checkBudget({ scopeType: 'user_id', scopeValue: 'team-y' });
// => { status: 'ok', budget: null, spent_usd: 0, limit_usd: null }
```

**The core query** (period start `$2` computed in JS per D1, not in SQL):
```sql
SELECT COALESCE(SUM(estimated_cost_usd), 0) AS spent
  FROM ai_inference.inference_requests
 WHERE {scope_column} = $1
   AND created_at >= $2
   AND estimated_cost_usd IS NOT NULL
```
`{scope_column}` is substituted from the D2 allowlist map — never from
`scopeType` directly.

## Acceptance Criteria

**MUST:**
1. `checkBudget()` returns `{status, budget, spent_usd, limit_usd}` matching
   the shape above, for all 5 scenarios in `s1.1-story.md`
2. Period window is calendar-based (D1), not rolling
3. `warn` when `spent_usd >= 0.8 * limit_usd`; `breach` when `spent_usd >= limit_usd`
4. `scope_type` validated against the D2 allowlist before use in SQL — reject anything else
5. `004_usage_budgets.sql` applies cleanly via `npm run migrate`

**SHOULD:**
1. Index on `usage_budgets(scope_type, scope_value, status)` for lookup
2. Index on `inference_requests`'s scope columns + `created_at` for the SUM query — baseline hygiene, not the "revisit only if profiling shows it's needed" maintained-counter question from epic scope.md's risks (that's about a *redundant running counter*, not an index)

**MUST NOT:**
1. Must not call governance-service, escalation-service, or any other network service — pure DB read + computation
2. Must not modify `inference.js`'s routes — that's S1.2
3. Must not throw/reject when no budget is found — that's a valid `ok` result (D3)
