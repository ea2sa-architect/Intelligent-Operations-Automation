# S1.4 Retrospective: Budget admin page

**Story:** S1.4 | **Epic:** E1 | **Size:** M | **Date:** 2026-08-03
**Time:** Estimated 240 min, actual ~120 min (velocity 2.0x) — low-confidence, same caveat as prior stories.

## What Went Well

- Following `TagAdmin.jsx`'s exact structure (not the epic design's original, wrong `WaiverAdmin.jsx` comparison) meant the UI code was nearly mechanical to write, and it rendered correctly first try.
- Mandatory Task 5 (real browser verification) did exactly what it was there for — it caught **two real, non-obvious bugs that mocked tests and code review would never have found**: (1) a stale `ai-inference-service` container running 6-day-old code with no `budgets.js` route at all, and (2) Kong's route config not allowing `DELETE`, which 404'd at the gateway before ever reaching the app. Neither is a logic bug; both are pure "does the actual running system agree with the source code" gaps.

## What to Improve

- I initially wrote a redundant second Vite dev server instead of noticing the user already had one running against the same working directory. Should check `lsof`/`ss` for an existing listener before starting a new one, not just trust that starting fresh is the default move.
- Killing the user's stale dev server needed their explicit confirmation first (correctly asked) — worth remembering that "the server is objectively stale" doesn't mean "kill it without asking," since it had an active connection that wasn't mine.

## Heutagogical Checkpoint

**1. What did you learn?** That "the code is correct" and "the running system reflects the code" are two separate claims, and this repo has two different gaps between them: Docker services need an explicit rebuild (no bind mount), and a long-lived Vite dev server can drift from disk state after enough git branch churn. Both are invisible to any test suite — only driving the real, running system surfaces them.

**2. What would you change about the process?** Nothing about the mandatory-Task-5 rule itself — it worked exactly as designed. I'd add a habit: check for an already-running dev server before starting a new one, and check container build timestamps before trusting a running service reflects current code.

**3. Are there improvements for the framework?** The `/rai-story-plan` template's "Manual integration test" guidance could explicitly prompt "is the target service's running container stale?" as a checklist item for any story touching a Docker-composed backend — this bit twice in one story (container staleness, then again implicitly via Kong routing) and neither was anticipated in the plan.

**4. What are you more capable of now?** A working Playwright-in-Docker verification recipe for this repo specifically (official `mcr.microsoft.com/playwright` image, `--network host`, existing dev server on 5173, `admin`/`<set at seed time>` test credentials) — directly reusable for S1.5 and the epic's own scheduled E2E checkpoint.

## Patterns Added

- **PAT-S-006** (technical): Kong routes allow-list HTTP methods explicitly — a routed path prefix doesn't imply every verb is allowed.
- **PAT-S-007** (process): backend containers here use `build:` context, not bind mounts — need explicit rebuild.
- **PAT-S-008** (process): long-running Vite dev servers can go stale after heavy git branch-switching; verify source before debugging "phantom" routing bugs.
