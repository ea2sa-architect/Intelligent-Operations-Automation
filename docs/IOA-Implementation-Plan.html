F1 — Policy enforcement mode field
EP-201-S1DB migration: add enforcement_mode ENUM ('observe','warn','enforce') to governance.policies
EP-201-S2API: PATCH /policies/:id/enforcement-mode — requires admin + audit trail write
EP-201-S3Governance UI: mode selector chip on policy detail (Observe / Warn / Enforce)
F2 — Kong gateway enforcement
EP-201-S4Kong plugin or pre-request webhook: call governance-service /enforce endpoint before MCP proxy requests
EP-201-S5Enforce mode: return 403 with policy_id + violation_id on block decision
EP-201-S6Warn mode: pass through, create violation, add X-IOA-Warning header
F3 — n8n pre-execution policy check
EP-201-S7n8n: IOA governance check as workflow start trigger (webhook to workflow-governance-service)
EP-201-S8Workflow-governance: evaluate all bound policies before execution approval
EP-201-S9Human approval gate response path for enforce-mode workflows requiring sign-off
EP-201-S15Remediation, found 2026-10-08: EP-201-S7/S8's enforcement-check route (and EP-102's execution-event) have no signature/replay protection at all — n8n Cloud can't hold the internal service key, but there's no HMAC fallback either. governance-service's own /enforce (S4/S5 above) also has no permission gate: any authenticated session, any role, can call it directly. Tracked as S2.1 (widened) + S2.8 in work/epics/e2-iso42001-hardening/; see docs/baseline-assessment-2026-10.md findings F-01/F-02.
F4 — Enforcement event recording
EP-201-S10DB migration: governance.enforcement_events (policy_id, asset_type, asset_id, mode, outcome, correlation_id, timestamp)
EP-201-S11Dashboard: enforcement activity count + block/warn ratio card

EP-201-S13Same evaluator checks inference_requests.data_classification against a policy-configured max-allowed classification per provider — blocks in enforce mode
EP-201-S14Scheduled reaper (matching approval-expiration-reaper.js's pattern) proactively re-verifies approved servers' live config against materiality_hash, reusing the existing revert-to-pending/deprovision/incident path — closes the "only reacts to an explicit PUT" gap
