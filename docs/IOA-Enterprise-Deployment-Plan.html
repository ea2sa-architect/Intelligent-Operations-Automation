EP-308 · Phase 1 · Weeks 1–4 ✓ SHIPPED

Fine-grained RBAC

Replace the coarse admin/guest model with named roles that map to real enterprise personas. A governance officer should not have the same access as a read-only auditor.

Phase 1 Required before first pilot
IDStoryEffortNotes
EP-308-S1 ✓
Define 5 named roles in DB migration
governance-officer — approve/reject MCP, create/edit policies, resolve violations, manage waivers
security-reviewer — review MCP servers, read all, add evidence, cannot approve
business-owner — read own team's servers and workflows, submit registrations
auditor — full read-only access + report export
platform-admin — all access including user management
 S · 2d Migration auth/003_named_roles.sql; seed defaults on first start
EP-308-S2 ✓
Named permission constants replacing coarse read/write
Replace 'write' with action-specific names: mcp:approve, mcp:register, policy:edit, violation:resolve, waiver:grant, user:manage. Embed resolved permission set in JWT.
 S · 2d Update auth-service/src/lib/seed-admin.js; update require-auth.js to check action-level claim
IDStoryEffortNotes
EP-308-S3 ✓
requirePermission(action) middleware helper
Extend require-auth.js with a curried requirePermission('mcp:approve') factory. Reads from JWT permissions claim array; 403 if absent.
 XS · 1d Propagate across all 8 services via byte-identical copy (existing pattern)
EP-308-S4 ✓
Annotate all mutating routes with required permission
Audit every POST/PUT/PATCH/DELETE across all 8 services. Apply requirePermission at route level. Document each route's required permission in a permissions matrix.

SPA permission-aware UI — hide/disable controls based on JWT claims

EP-306 · Phase 2 · Weeks 3–9 · Critical Path ✓ SHIPPED

MCP Discovery Engine

The most critical gap for corporate deployment. Without discovery, the platform requires clients to know what to govern before governance starts — which defeats the purpose. Three discovery vectors, delivered in order of coverage-per-effort.

Phase 2 Critical path for enterprise pitch
IDStoryEffortNotes
EP-306-S12 ✓
API key authentication for discovery-agent
New auth.api_keys table (name, key_hash, scopes[], created_by, last_used_at, revoked_at). requireApiKey checks an X-IOA-Api-Key header before falling through to session/service-key auth, resolving to a synthetic req.user scoped to only the key's granted permissions. POST /auth/api-keys (platform-admin/governance-officer, user:manage-gated, key shown once) and DELETE /auth/api-keys/:id to revoke.
 M · 4d Added during scoping review: S1/S4's own notes assume "a dedicated API key (not a user JWT)" exists, but neither this epic nor EP-307 (Enterprise Auth) actually builds one — session-JWT and the single shared INTERNAL_SERVICE_KEY are the only two auth paths that exist today, and neither fits an unattended CLI running on a developer laptop or in CI. Blocks S1–S9; sequence first.
EP-306-S1 ✓
Claude Desktop config parser
Parse ~/.claude/claude_desktop_config.json (and Windows/Linux equivalents) to extract mcpServers entries. Output: server name, command, args, env hints.
 S · 2d New service: discovery-agent — a lightweight Node.js CLI, not a full Express service
EP-306-S2 ✓
VS Code MCP settings parser
Parse .vscode/settings.json and ~/.vscode/extensions/*/package.json for MCP server registrations in the Claude/Cline extensions.
 S · 2d Same discovery-agent; different parser module
EP-306-S3 ✓
Cursor and Windsurf config parsers
Parse Cursor's ~/.cursor/mcp.json and Windsurf's equivalent MCP config location. These two IDEs have fast-growing enterprise adoption.
 XS · 1d Same pattern — just different paths and JSON schemas
EP-306-S4 ✓
Discovery report → IOA import API
Discovery agent sends discovered servers to POST /mcp-governance/servers/discovery-import. Each server submitted as a candidate with status='discovered' and source metadata. Idempotent on server name.
 S · 3d New status value 'discovered' in mcp_servers; migration required. No unique constraint exists on mcp_servers.name today — the idempotent-upsert lookup needs to key off (name, status='discovered') explicitly, not rely on a DB constraint.
EP-306-S13 ✓
Discovery scan history + diff computation
New mcp_governance.discovery_scans table storing each run's raw results per source (config-file, GitHub, Docker, network). On each new scan, diff against the prior scan for the same discovered server (by name + source) and compute field-level changes (new tool, changed endpoint, etc.) for S5's review UI to render.
 S · 3d Added during scoping review: S5 references a "diff view" but nothing upstream persists prior-scan state to diff against — this is the storage/computation S5's UI needs.
EP-306-S5 ✓
SPA: Discovery queue review UI
New tab in MCP Governance page: "Discovered" showing all status='discovered' servers. Governance officer can promote to pending_review (starts formal process) or dismiss. Diff view shows what changed since last discovery run.
 M · 4d This is the primary interaction surface for the discovery workflow
Architecture: discovery-agent is a standalone CLI package (packages/discovery-agent/) that runs locally on the developer's machine or via CI. It authenticates to the platform API using a dedicated API key (not a user JWT). It does not need to be always-running.

EP-307 · Phase 2 · Weeks 3–7 · Parallel with EP-306 ◐ PARTIAL — CLI key exchange only

Enterprise Authentication

Replace local username/password with enterprise identity systems. OIDC is the highest-priority deliverable; SAML and LDAP follow. MFA is a hard requirement for any platform that can block AI tool execution.

Phase 2 Hard requirement for enterprise
IDStoryEffortNotes
EP-307-S1
OIDC provider configuration in auth-service
Add openid-client library. Configure via env: OIDC_ISSUER, OIDC_CLIENT_ID, OIDC_CLIENT_SECRET, OIDC_REDIRECT_URI. Support Okta, Azure AD, Google Workspace, Keycloak.
 S · 3d auth-service gains GET /auth/oidc/login and GET /auth/oidc/callback routes
EP-307-S2
OIDC claims → IOA role mapping
Map OIDC group claims (groups or roles) to IOA roles via configurable mapping: OIDC_ROLE_MAP={"security-team":"governance-officer","audit-team":"auditor"}.
 S · 2d JIT provisioning: user record created on first login if not exists
EP-307-S3
SPA OIDC login flow
When OIDC is configured, show "Sign in with SSO" button on login page. Redirect to provider, handle callback, exchange for IOA JWT. Fall back to local login only if explicitly enabled.
 S · 2d Update web/src/pages/Login.jsx; detect OIDC via GET /auth/config endpoint
EP-307-S4
SAML 2.0 support (for legacy enterprise IdPs)
Add samlify or passport-saml. Configure via SP metadata endpoint. Required for older Okta orgs and Microsoft ADFS environments that haven't moved to OIDC.
 M · 4d Can defer to 1.1 if OIDC covers first pilot customer
IDStoryEffortNotes
EP-307-S5
TOTP MFA for local auth (Google Authenticator / Authy)
Add otplib to auth-service. POST /auth/mfa/setup returns QR code, POST /auth/mfa/verify validates TOTP. MFA required for governance-officer and platform-admin roles.
 M · 4d Store TOTP secret encrypted in auth.users; migration required. OIDC logins delegate MFA to the IdP — no extra work.
EP-307-S6
MFA enforcement policy — block high-privilege actions without MFA
Short-lived elevated JWT (15 min) issued after MFA verification. Server requires mfa_verified: true claim for mcp:approve, waiver:grant, and user:manage actions.
 S · 2d Pattern: "sudo mode" — existing JWT still valid for read; elevated token required for writes on high-privilege routes
IDStoryEffortNotes
EP-307-S7
Refresh token rotation with Redis session store
Current 60-minute JWT has no refresh. Add refresh token (7-day) stored in Redis. Implement POST /auth/refresh. Invalidate all sessions on role change or account deactivation.
 S · 2d Redis is already in compose; use it here
EP-307-S8
Active session list + force-logout for admins
GET /auth/sessions lists active sessions for a user. DELETE /auth/sessions/:id invalidates a specific session. DELETE /auth/sessions/all for full force-logout (user:manage required).
 S · 2d Add session management tab to User Management page in Admin section

Deployment Package

Make the platform installable by a corporate IT team without needing the original developers involved. Helm chart, TLS, and externalized secrets management are the three gates.

Phase 3 Gates first customer install
IDStoryEffortNotes
EP-309-S1
Helm chart scaffold for all 9 services
Create helm/ioa-governance/ with a single chart covering all services. Use subcharts for DB (TimescaleDB Helm chart) and Redis. values.yaml exposes every tunable without editing templates.
 M · 4d Extends existing K8s manifests; they become the template source
EP-309-S2
values.yaml profiles: minimal, standard, ha
minimal: 1 replica each, no HA DB — for pilots and dev
standard: 2 replicas, managed DB external
ha: 3 replicas, TimescaleDB HA cluster, Redis Sentinel
 S · 2d Each profile is a values-minimal.yaml override file
EP-309-S3
Migration Job as Kubernetes Job resource
Convert db/migrate.js to a K8s Job that runs on helm install/upgrade as a Helm hook. Eliminates the manual "run migrations" step.
 S · 2d Use helm.sh/hook: pre-upgrade,pre-install annotation
EP-309-S4
Ingress with TLS termination (nginx/traefik)
Helm chart includes ingress resource with TLS annotations for cert-manager (cert-manager.io/cluster-issuer: letsencrypt-prod). Single hostname routes all service traffic through Kong.
 S · 2d Kong sits behind the ingress; ingress handles TLS, Kong handles routing
IDStoryEffortNotes
EP-309-S5
cert-manager integration for auto-certificate provisioning
Add cert-manager as a Helm dependency. Configure ClusterIssuer for Let's Encrypt (public) and a self-signed issuer for internal namespaces. Certificates auto-renew.
 S · 2d Alternatively: support BYO certificate via secret name in values.yaml
EP-309-S6
Internal mTLS between services (Istio or cert-manager)
Service-to-service traffic inside the cluster must use mTLS. Preferably via a service mesh (Istio, Linkerd) but can be done with per-service certificates from cert-manager if no mesh is available.
 M · 3d Flag as optional in values.yaml (mtls.enabled: true) — requires cluster support
IDStoryEffortNotes
EP-309-S7
External Secrets Operator integration
Use the External Secrets Operator to sync secrets from AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault into K8s Secrets. Helm chart generates ExternalSecret resources pointing at configurable store.
 M · 3d Three store backends: AWS, Azure, Vault — configure via secretStore.type in values.yaml
EP-309-S8
Remove all .env file dependencies from K8s deployment path
K8s deployment must work with zero .env files. All secrets come from K8s Secrets (backed by ESO or manually created). .env file path remains for docker-compose dev only.
 S · 2d Update all service Dockerfiles to not expect .env at runtime
IDStoryEffortNotes
EP-309-S9
Prometheus metrics endpoint on all services
Add prom-client to each service. Expose GET /metrics. Standard: request latency, error rate, DB pool saturation. Custom: violation count by severity, anomaly alerts by type.
 S · 2d Reuse require-auth.js pattern — single metrics.js added to each service
EP-309-S10
Structured JSON logging with correlation IDs
Replace console.log with pino structured logger. All log lines include: service, level, correlation_id (from request header), timestamp. Enables log aggregation (Loki, Datadog, CloudWatch).
 S · 2d One logger.js shared pattern; add to each service
EP-311 · Phase 4 · Weeks 10–16 · v1.1 Milestone ○ NOT STARTED

Multi-tenancy

Enable a single deployment to serve multiple business units with data isolation. The CISO and platform-admin see everything; each business unit sees only their own data. This is complex — scope carefully.

Phase 4 v1.1 Milestone
IDStoryEffortNotes
EP-311-S1
org_id + team_id columns on all tenant-scoped tables
Add org_id UUID NOT NULL and optional team_id UUID to: mcp_servers, workflows, violations, policies, audit_events. Non-nullable with DEFAULT for current single-org data.
 L · 5d Most invasive migration in the plan — all existing data needs org_id assigned. Create public.organisations table first.
EP-311-S2
Row-level security (RLS) policies on all tenant tables
Enable Postgres RLS on all org-scoped tables. Policy: USING (org_id = current_setting('app.current_org_id')::uuid). Each service sets this setting on the connection from the JWT claim.
 L · 5d Requires updating all service db.js connection setup. Test extensively — RLS bypasses are subtle.
EP-311-S3
Organisation management UI and API
platform-admin can create organisations, invite users, assign org-level roles. Each org gets its own governance-officer and auditor roles scoped to that org.
 M · 4d New Admin page: Organisation Management
IDStoryEffortNotes
EP-311-S4
Platform-admin bypass for RLS (aggregate queries)
platform-admin role bypasses RLS to see all orgs. Requires a separate DB role (ioa_superuser) with BYPASSRLS. Used only for aggregate Dashboard queries — not exposed through normal service path.
 M · 3d Audit every use of BYPASSRLS — this is a privileged path
EP-311-S5
Organisation-scoped policy inheritance
Platform-level policies (owned by org_id=platform) apply to all orgs. Each org can add org-specific policies. Business unit can add team-specific policies. Violation evaluation walks the inheritance chain.
 L · 5d Significant policy engine change — design carefully before implementing
EP-311-S6
Aggregate CISO dashboard
New Dashboard view (platform-admin only) showing: open violations by org, MCP servers pending review across all orgs, anomaly alert counts by org, compliance posture heatmap.
 M · 4d New page: web/src/pages/CISODashboard.jsx — accessible only with platform-admin role
