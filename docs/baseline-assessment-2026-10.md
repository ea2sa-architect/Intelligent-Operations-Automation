# IOA Governance Platform — Investigative Baseline Assessment

**Date:** 2026-10-08
**Scope:** All 8 platform services (governance, ai-inference, audit, escalation, telemetry, workflow-governance, mcp-governance, auth), the `web/` SPA, Kong configuration and the `ioa-mcp-enforcement` plugin, CI/CD, and secrets handling.
**Method:** Read-only code/config inspection (no runtime testing against a live deployment). Every claim below cites a file:line. Absence of evidence is stated explicitly rather than omitted.

---

## Modernization Gate

Architecturally, these findings set the gate for any further work: **policy, MCP, or workflow feature expansion should not proceed until IOA establishes four minimum controls**, each tracing directly to a Critical/High finding below:

1. **Authorization on `/enforce` and the workflow enforcement check** (F-01, F-02) — the platform's central decision and execution gates currently have no permission gate and no authentication, respectively.
2. **Signed, replay-protected workflow execution requests** (F-02) — extend the existing `N8N_WEBHOOK_SECRET` HMAC pattern (already implemented for the analyze/callback route) to `enforcement-check` and `execution-event`.
3. **Authenticated identity binding for every audit and approval write** (F-04, F-05) — `actor_id`/`actor`/`requested_by` must be derived server-side from the authenticated caller, not accepted verbatim from the request body, on every human-session-reachable route.
4. **Server-derived release-certification evidence** (F-06) — `release-decisions.js` must re-query real violation state rather than trusting a caller-supplied evidence bundle.

These four are called out separately from the rest of the Findings Register (D) because they are the ones that specifically gate *new* feature work, rather than general hardening — building more policy/MCP/workflow surface on top of an unenforced decision point or a forgeable evidence trail compounds the exposure rather than isolating it.

## A. Executive Baseline

**Overall maturity: a mix, with real enforcement islands inside a much larger observational/prototype surface.** This is not primarily an enforcement platform, nor primarily an observation platform — it is architecturally closer to a prototype that has grown two or three genuinely enforced control points without the surrounding scaffolding (CI gates, tenant isolation, consistent provenance capture, consistent auth-coverage review) a production governance platform would need.

**Strongest foundations:**
- A real, fail-closed BLOCK enforcement path exists and is consumed by two independent callers: governance-service's `POST /enforce` and the Kong `ioa-mcp-enforcement` Lua plugin (cache-fronted, synchronous, `fail_mode: "closed"` by default). MCP server approval has a genuine, traceable side effect — live Kong service/route/plugin provisioning, not just a database flag.
- `require-auth.js`'s identity/CSRF logic and the EP-308 named-permission model are consistently fail-closed across every env-var/config-missing path checked (JWT key absent → 500, no token → 401, verify throws → 401, agent-revocation DB error → 401, missing permission → 403).
- audit-service's API surface is genuinely append-only — no PATCH/PUT/DELETE route exists at all.
- Containment (`containment-client.js`) is deliberately not fail-soft: a kill switch that can't confirm success does not log success.
- The frontend's governance-action controls (policy enforcement-mode toggle, MCP server approve/reject) are real, backend-enforced mutations, not cosmetic — verified by tracing to DB writes and Kong provisioning.

**Most consequential gaps:**
- The main policy-decision endpoint, `POST /enforce`, has **no permission gate** — its own code comment claims it's "still covered by the existing coarse write-permission check in require-auth.js," but that check was removed under EP-308-S4 (confirmed in `require-auth.js`'s own changelog comment). Any authenticated session of any role can trigger live rule evaluation and violation writes.
- The workflow-execution gate itself, `POST /workflows/:id/enforcement-check`, is unauthenticated with zero signature/replay protection — a deliberate, documented tradeoff (n8n Cloud has no service-key path), but undocumented in CLAUDE.md, which names only two of the three such routes.
- No tenant/organization/realm isolation exists anywhere in the 6 core services — a single flat global namespace.
- Several append-only trails (audit events, approval decisions, approval-chain requester identity) trust client-supplied identity fields with no cross-check against the authenticated caller.
- CI (`Jenkinsfile`) runs zero tests, lint, SAST, secret scanning, or dependency audit before deploying the SPA to production.
- ATI/trust-ceiling scoring — the platform's most visible "trust tier" concept — is entirely observational; it is computed, stored, and displayed, but never consulted by any enforcement path.

**Must be verified before modernization begins:**
- Whether the `ioa-mcp-enforcement` Lua plugin is actually loaded (`KONG_PLUGINS` env) on the live shared Kong instance right now — this repo cannot confirm that from static inspection alone.
- Whether n8n's own workflow JSON actually treats an `enforcement-check` 403 as a hard-stop branch — the HTTP contract is correct on this side, but the wiring lives in n8n, outside this repo.
- Decide, as a scoped product/architecture question (not a bug to patch), whether the modernization introduces tenant isolation — it is absent today by design-by-omission, not by a flaw in an existing mechanism.

**One action item independent of this report:** while gathering evidence for this baseline, a research subagent's own redaction logic failed while summarizing a local `.env` file and briefly echoed real secret values (a private key, the OIDC client secret, N8N API keys, `INTERNAL_SERVICE_KEY`) into one of its own tool outputs during this session. No secret values are reproduced anywhere in this report or in any file written during this investigation. As a precaution, independent of and before any modernization work, rotate: `INTERNAL_SERVICE_KEY`, the Keycloak OIDC client secret, and the N8N API keys (`N8N_API_KEY`/`N8N_CLOUD_API_KEY`/`N8N_LOCAL_API_KEY`).

## B. Current-State Architecture (implemented, not aspirational)

**Components:** 8 Node/Express services, each with its own Postgres schema in a shared TimescaleDB instance, fronted by a **shared** Kong gateway (owned by a sibling infrastructure project, not this repo) and a React SPA. governance-service is the policy/decision/audit-evidence hub; ai-inference-service governs model calls and usage budgets; audit-service is an append-only event store; escalation-service manages incidents/rules; telemetry-service ingests execution/metrics data; workflow-governance-service imports and risk-scores workflows from n8n/Make/Zapier/Camunda; mcp-governance-service registers, approves, and scores MCP servers/tools; auth-service issues/manages sessions, API keys, and agent-delegation credentials, resolving roles→permissions from Postgres and embedding them in short-lived (60m, 15m for agents) RS256 JWTs.

**Trust boundaries:**
- *Browser → services*: httpOnly session cookie + double-submit CSRF cookie, verified identically (byte-for-byte duplicated `require-auth.js`) in all 8 services except auth-service (issuer, not consumer).
- *Service → service*: a shared `INTERNAL_SERVICE_KEY` header, checked before falling through to JWT verification (fails closed if unset).
- *n8n → workflow-governance-service*: the one boundary with materially weaker protection — 3 routes bypass `requireAuth` entirely (one optionally HMAC-signed, two with no protection at all). See Finding F-01/F-02.
- *Kong → services, and direct port → services*: identical — Kong adds only rate-limiting, no auth-relevant plugin on any of the platform's 9 routes. Direct container-port access bypasses Kong's rate limiting but not the service's own auth (an accepted risk per CLAUDE.md).
- *mcp-governance-service → Kong (per-approved-server)*: a distinct, dynamic provisioning path (`kong-provisioner.js`) separate from the static `kong.yaml`/`deck` sync used for the 8 fixed services.

**Decision and audit flows:** The one real cross-cutting decision point is governance-service's `POST /enforce`: it checks containment state, re-evaluates applicable rules, and for each bound policy returns `allow`/`warn`/`block` based on `enforcement_mode`, writing one `enforcement_events` row per policy per call regardless of outcome. Two independent callers consume this: workflow-governance-service's n8n-facing gate, and the Kong Lua plugin (for MCP traffic). Audit evidence beyond this is split: `governance.violation_history` snapshots the policy version at each lifecycle transition (not at creation); `audit-service` captures a structured but caller-asserted event record with no cross-check against the authenticated caller's real identity; `escalation.incidents` captures no rule-condition snapshot at all.

**Identity/authentication posture:** EP-308's named-permission model (role→permission resolved at login/`,/me`, baked into the JWT at issuance) is consistently and correctly fail-closed everywhere it was checked. The one exception to coverage, not to fail-closed-ness, is `POST /enforce`'s missing `requirePermission` gate (Finding F-01).

**Key dependencies / SPOFs:** the shared Postgres/TimescaleDB instance (single DB container, port published to host with no bind restriction); the shared Kong instance (owned outside this repo, shared with unrelated teams — `deck gateway sync` without `--select-tag` has already caused one incident per CLAUDE.md); n8n (cloud, external); Keycloak/OIDC (external, referenced in `.env` and `docs/keycloak-realm-ioa.json`); `redis-master`, referenced by workflow-governance-service's `REDIS_URL` env var but **not itself defined as a service in `docker-compose.yml`** — an undocumented external dependency from this file's perspective.

## F. Modernization Readiness — Five Sequenced Next Steps

**Required before adding new features:**
1. Close F-01 (`/enforce`'s missing permission gate) and F-02 (document, and decide whether to protect, the third unauthenticated n8n webhook) — these sit on the platform's central decision/execution path; building new capability on top of an unclosed gap here compounds the exposure.
2. Stand up CI gates (F-08): at minimum, run the existing backend test suite (`node scripts/test-all.js`) and add a lint command before any deploy step — right now nothing automated stands between a regression and production.

**Can be built incrementally afterward:**
3. Close the provenance-trust gaps (F-04, F-05, F-06) one route at a time — each is independent and low-risk to fix (derive identity server-side, re-query real violation state) without a broader redesign.
4. Add liveness signals for the 6 reapers (F-12) and fix the budget fail-open regression (F-03) — both are localized, well-understood fixes with existing design docs (ADR-002) to fix *toward*.

**Controls suitable for deterministic CI or gateway enforcement rather than prompt-based review:**
5.
